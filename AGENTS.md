## 1. Что это за проект

**iCook / «Я готовлю — ты ешь!»** — сайт доставки домашней еды.

Основные сценарии:

- покупатель смотрит меню и рестораны, кладёт блюда в корзину, оформляет заказ;
- продавец (шеф) регистрируется, становится продавцом, публикует блюда и обрабатывает заказы;
- пользователь регистрируется, подтверждает email, меняет/восстанавливает пароль, удаляет аккаунт.

## 2. Текущая архитектура

### 2.1 Общая схема

```
 Браузер
    │  HTML + CSS + JS (статические страницы в корне репозитория)
    │  fetch('/api/....php')  ──►  JSON
    ▼
 Apache + PHP 8.2                    (контейнер web)
    │  PDO (prepared statements)
    ▼
 MySQL 8                             (контейнер db)
    ▲
 phpMyAdmin (8081) — просмотр БД
 Mailpit   (8025) — перехват писем от PHP mail()
```

Ключевой принцип: **фронтенд статический, вся логика — в PHP-эндпоинтах `api/`**,
которые отвечают JSON вида `{"success": ...}` или `{"error": "..."}`.
Взаимодействие — через `fetch()` с относительными путями `/api/...`,
поэтому всё работает на одном origin.

### 2.2 Стек

| Слой       | Технология                                              |
|------------|---------------------------------------------------------|
| Фронтенд   | Чистый HTML/CSS/JS (без сборщика и фреймворков)         |
| Бэкенд     | PHP 8.2 (Apache + mod_php), PDO/MySQL                   |
| БД         | MySQL 8.0, кодировка `utf8mb4`                          |
| Упаковка   | Docker, Docker Compose                                  |
| Зависимости| Composer (PHPMailer в `vendor/`, в коде пока не используется) |
| Почта      | PHP `mail()` → msmtp → Mailpit (только в dev)           |
| CI         | GitHub Actions (`.github/workflows/ci.yml`): php -l + docker build |

### 2.6 Окружение

- Параметры БД читаются из env: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`.
- Секреты живут только в `.env` (в Git не коммитится). В коде секретов нет.
- Порты по умолчанию: web 8080, phpMyAdmin 8081, Mailpit 8025/1025, MySQL 3307.

## 3. Правила работы агента

### 3.1 Язык и стиль

1. Общение с пользователем, комментарии, коммиты и документация — **на русском**.
2. Код (имена переменных, функций, таблиц, эндпоинтов) — по существующему стилю:
   английские идентификаторы, PHP в процедурном стиле (как в `api/*.php`).
3. Не переформатировать существующие файлы целиком «для красоты». Делать
   минимальные точечные изменения.

### 3.2 Безопасность (обязательно)

1. **Никогда не коммитить секреты.** Пароли, токены, ключи — только через
   переменные окружения / `.env` (файл указан в `.gitignore`).
2. Все SQL-запросы — только через **PDO prepared statements** (`prepare` + `execute`).
   Конкатенация переменных в SQL запрещена.
3. Пароли — только `password_hash()` / `password_verify()`.
4. Данные, приходящие от пользователя, валидировать: email — `filter_var(...)`,
   числа — `filter_var(..., FILTER_VALIDATE_INT)`.
5. Не логировать и не возвращать в JSON пароли и токены.
6. Не добавлять отладочный вывод секретов даже в dev-режиме.

### 3.3 API и БД

1. Новые эндпоинты — в `api/`, имя файла в `snake_case` (`add_dish.php`).
2. Формат ответа единый: `{"success": true, ...}` или `{"error": "текст"}`;
   заголовок `Content-Type: application/json`.
3. Если эндпоинт требует авторизации — проверять `$_SESSION['user_id']` и
   возвращать `{"error": "Не авторизован"}`.
4. Публичные URL (`/api/имя.php`) и имена таблиц/колонок менять только осознанно
   и с обновлением всех вызовов во фронтенде.
5. Изменения схемы БД — отдельными SQL-файлами в `docker/mysql/init/`
   с возрастающим префиксом (`02_...`, `03_...`), с комментарием-назначением.

### 3.4 Docker

1. Приложение должно оставаться запускаемым одной командой:
   `docker compose up -d --build`.
2. Не «зашивать» секреты в `Dockerfile` и `docker-compose.yml` — только `${...}` из `.env`.
3. Новые системные/php-расширения добавлять в `Dockerfile`
   (`docker-php-ext-install`) и документировать в README.
4. После правок `docker-compose.yml` проверять `docker compose config`.

### 3.5 Git и CI

1. Ветка по умолчанию — `main`.
2. Сообщения коммитов — **Conventional Commits**:
   `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `ci:`, `test:`
   (например: `feat: добавлен api/dishes.php`).
3. Не коммитить `vendor/`, `.env`, `uploads/*`, папки `_notes/`, `dwsync.xml`.
4. Перед коммитом PHP-код должен проходить `php -l` (это же делает CI).

### 3.6 Что трогать нельзя без явной просьбы

1. `mail/` — это legacy-копия Roundcube, в рантайме не участвует. Не рефакторить.
2. `vendor/` — генерируется Composer, редактировать вручную нельзя.
3. Уже опубликованные страницы и URL не переименовывать.

### 3.7 Работа с задачами

1. Сначала — осмотр и план, потом изменения.
2. После изменений обязательно: проверка синтаксиса PHP, при необходимости —
   перезапуск/пересборка контейнеров и проверка ответа сайта.
3. Если задача затрагивает архитектуру, эндпоинты, схему БД или окружение —
   **обновить этот файл (AGENTS.md)** и `README.md`.

## 4. Известные проблемы и технический долг

1. **Отсутствует часть API** (`dishes.php`, `categories.php`, `orders.php` и др.) —
   страницы меню, корзины и кабинета не работают полностью.
2. **Схема БД реконструирована** по коду и требует сверки с продакшеном.
3. **Дублирование кода во фронтенде**: модалка входа/регистрации и вспомогательный
   JS скопированы в каждый HTML-файл.
4. **`assets/js/auth.js`** — упрощённая заглушка: логин сохраняется в `localStorage`
   без обращения к серверу.
5. **`assets/js/config.js`** содержит закомментированные вебхуки n8n
   (`/webhook/...`) — неиспользуемый альтернативный бэкенд.
6. **PHPMailer установлен, но не используется**: письма шлются через `mail()`.
7. Медиа — большие встроенные CSS/JS в HTML и локальный `assets/apk/ICOOK.apk`.
